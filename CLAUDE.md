## Project overview

Industrial quality-control app for a corrugated-cardboard packaging plant: a Flutter mobile client (`lib/`) paired with a Node.js/Express + MySQL backend (`backend/`). Operators scan a QR code on a machine, get an auto-generated form based on machine/process, and submit quality-control records — with offline support when plant Wi-Fi or mobile data is unavailable.

In Git Bash on Windows, a leading `/` argument gets mis-expanded to a Windows path (`C:/Program Files/Git/qualitycontrol/`) — prefix the command with `MSYS_NO_PATHCONV=1` if that happens. Deploy by uploading the full contents of `build/web/` to the corresponding path, overwriting existing files.

Known gotcha: Flutter web registers a service worker that aggressively caches `main.dart.js`. After redeploying, clients (including yourself while testing) may keep executing an old cached bundle — regular "clear browsing history" does **not** reliably clear Service Worker/Cache Storage. If a deployed change doesn't seem to take effect in the browser but a fresh `curl` of the deployed `main.dart.js` shows the new code, it's this cache: DevTools → Application → Service Workers → Unregister, then Application → Clear storage → Clear site data, then close all tabs of that origin before reopening.

### Android APK build (Gradle/JDK toolchain)

```
flutter build apk --dart-define=API_BASE_URL=https://api.faret.cl/calidad/api
```

The `android/` project was migrated (2026-07-07) off the original ancient Flutter template config (Gradle 7.5, AGP 7.2.0, Kotlin 1.7.10, imperative `apply plugin:`/`apply from:` in `settings.gradle`/`app/build.gradle`) to what the currently installed Flutter SDK (3.44.4) actually requires: **Gradle 8.14, AGP 8.11.1, Kotlin 2.2.20**, declarative `plugins {}` blocks, and an explicit `namespace` in `app/build.gradle`. Gradle 7.5 can't even resolve Flutter's own `flutter_tools/gradle` included build on this SDK (fails with `Unsupported class file major version 65` under JDK 21, and separately with a missing `org.gradle.kotlin.kotlin-dsl` plugin under any Gradle <8 regardless of JDK).

Toolchain requirements to build the APK on this machine:
- **JDK 17** (Eclipse Temurin, installed via `winget install EclipseAdoptium.Temurin.17.JDK`) — Gradle 8.14 needs a JDK it supports; Android Studio's bundled JBR is JDK 21. Pinned via `org.gradle.java.home` in `android/gradle.properties` — don't remove that line, or Gradle silently falls back to whatever JBR/JDK Android Studio ships, which can drift across Android Studio updates and reintroduce the JDK-version build failure.
- Kaspersky on this machine intercepts TLS, which breaks the Gradle wrapper's plain-JVM download of `gradle-8.14-all.zip` from `services.gradle.org` (`PKIX path building failed: unable to find valid certification path`). The wrapper's bootstrap JVM runs *before* `gradle.properties`/`org.gradle.jvmargs` take effect, so the fix must be an env var, not a Gradle setting. A truststore with Kaspersky's cert already imported lives at `.certs_tmp/cacerts_jdk17` (gitignored, machine-local — rebuild with `keytool -importcert -file .certs_tmp\kaspersky.cer -keystore .certs_tmp\cacerts_jdk17` against a copy of the JDK 17 `lib/security/cacerts` if it's missing or JDK 17 gets reinstalled). Build with:
  ```
  export JAVA_HOME="C:\Program Files\Eclipse Adoptium\jdk-17.0.19.10-hotspot"
  export JAVA_TOOL_OPTIONS="-Djavax.net.ssl.trustStore=<repo path>\.certs_tmp\cacerts_jdk17 -Djavax.net.ssl.trustStorePassword=changeit"
  flutter build apk --dart-define=API_BASE_URL=...
  ```
- `android/build.gradle` has a `subprojects { afterEvaluate { ... } }` block that backfills `namespace` from each subproject's `AndroidManifest.xml` `package` attribute — AGP 8 requires `namespace` on every Android library module, and some Flutter plugins pinned to old versions don't declare it (this is what originally broke on `connectivity_plus` 3.0.6, see the pubspec note below). That block must stay registered *before* the `subprojects { project.evaluationDependsOn(':app') }` line right after it in the file, or Gradle throws `Cannot run Project.afterEvaluate(Closure) when the project is already evaluated` — evaluationDependsOn forces early evaluation of `:app` that would otherwise beat the hook registration.

Output: `build/app/outputs/flutter-apk/app-release.apk`. It's a universal APK (`arm64-v8a`/`armeabi-v7a`/`x86_64` native code), `minSdkVersion 24`, signed with the **debug** keystore (`signingConfig signingConfigs.debug` in `app/build.gradle`, an unchanged TODO from the original template) — fine to sideload directly on a device, not fine to publish to the Play Store as-is.

### Backend (Node/Express, run from `backend/`)

```
cd backend
npm install
npm run dev     # nodemon, auto-restart
npm start       # node server.js
```

Backend requires `backend/src/config/database.js` (git-ignored) with a MySQL `mysql2` pool — copy `backend/src/config/database.example.js` and fill in real credentials. It also reads a `.env` for `PORT`/`DB_NAME`/etc. Never commit `database.js` or `.env`.

Production backend runs on Windows behind IIS, reverse-proxied via a URL Rewrite rule (`^calidad/(.*)` → `http://localhost:3000/{R:1}`; a sibling rule proxies `^fps/(.*)` → `http://localhost:3002/{R:1}` for an unrelated API hosted from the same site) — physical `server.js` at `C:\API WEB\api\calidad\server.js`.

**Correction (2026-07-20): the `web.config` with those rewrite rules is NOT inside `C:\API WEB\api\calidad\`** — that folder has no `web.config` of its own. It lives at the IIS site root and is shared between the `calidad` and `fps` rules. Practical consequence: if `calidad` responds fine on `localhost:3000` directly but fails through `https://api.faret.cl/calidad/...`, and the sibling `fps` API works fine through the same site, the problem is in that shared site-root config or the IIS layer generally — not in the Node app. Full incident writeup + a step-by-step safe deploy/restart procedure (validated in production) lives in `CONTEXTO_DESPLIEGUE_API_CALIDAD_SERVIDOR_161.md` at the repo root — **that file (like all `.md` files as of 2026-07-20) is gitignored** because it documents internal IPs/paths, so it only exists locally; regenerate it from memory/this section if it's missing.

Read-only file access to the production folder without RDP: `\\192.168.1.161\calidad` (SMB share, maps 1:1 to `C:\API WEB\api\calidad`) — enough to back up, diff, and copy deploy files, but not to restart the process (no remote exec channel).

**Correction to a previously wrong assumption: this is NOT managed by iisnode.** The Node process is a plain standalone `node.exe` (found at `C:\Program Files\nodejs\node.exe` — not on PATH) that has to be started manually in a console window, e.g.:
```
taskkill /F /IM node.exe
cd "C:\API WEB\api\calidad"
"C:\Program Files\nodejs\node.exe" server.js
```
(or `start "CalidadAPI" cmd /k "C:\Program Files\nodejs\node.exe" server.js` to run it in a background window that survives closing the current session). There's no auto-recovery/supervision on crash, but as of 2026-07-20 there IS a manually-triggered restart mechanism (correcting an earlier wrong claim that none existed): `C:\API WEB\reiniciar-calidad.bat` and a scheduled task `CalidadApi` (`schtasks /Run /TN CalidadApi`), neither of which auto-runs on crash/reboot — someone still has to trigger them. Consequences:
- `iisreset` does **NOT** restart this process — it only cycles IIS/w3wp (it does NOT kill other Node processes on the box either, safe to use for IIS-layer issues).
- **Always kill by specific PID, never `taskkill /F /IM node.exe` blindly** — other unrelated Node processes can be running on the same server and that command kills all of them. Resolve the right PID first: `netstat -ano | findstr :3000`.
- **A "restart" can silently not restart anything.** Confirmed in production 2026-07-20: the restart script reported success and the console showed the startup log line, but the OLD code kept serving for several attempts. The only way to actually confirm the new code is live: compare the deployed file's mtime against the listening PID's start time — `netstat -ano | findstr :3000` for the PID, then `powershell -Command "Get-Process -Id <PID> | Select-Object StartTime"`. If `StartTime` predates the file copy, the process still has old code — kill that exact PID and relaunch.
- If the console window running it is closed, or the process dies for any other reason, the **entire API goes down** with no auto-recovery — IIS proxies to a dead port and returns `502 Bad Gateway`. Verify liveness with `netstat -ano | findstr :3000`.
- TODO (not done yet): wrap it with [NSSM](https://nssm.cc/) as a real Windows service with `AppExit Default Restart` so it survives crashes/reboots.

**Remote deploy/restart without RDP (validated 3 times: 2026-07-20, 2026-08-10, 2026-08-17):** a full deploy+restart cycle is possible entirely from the dev machine via SMB (`\\192.168.1.161\calidad`, file copy) + WMI/DCOM (`Get-WmiObject`/`Invoke-WmiMethod ... Win32_Process Create`/`.Terminate()` on a specific verified PID) — no RDP, no interactive session needed. WinRM/PowerShell Remoting does **not** work (IP isn't in `TrustedHosts`). The exact copy-pasteable step-by-step (backup → copy+hash-or-diff-verify → identify+verify PID by `CommandLine` → `Terminate()` that exact PID → relaunch via `start-calidad-api.cmd` → verify new PID/`CreationDate`/log/endpoints → clean up temp files) lives in `PROCEDIMIENTO_DEPLOY_REMOTO_WMI_SERVIDOR_161.md` at the repo root (gitignored, local-only like all `.md` files added after 2026-07-20 — see below). **Never `taskkill /IM node.exe`** — the FPS API (port 3002) runs as a sibling `node.exe` on the same box and would die too; always terminate by exact verified PID.

The IIS site `API` (id 2, bindings `api.faret.cl:80`/`:443`) also hosts several unrelated apps as separate IIS Applications sharing the same site and SSL certificate: `appguardias`, `mejora-continua`, `formularios`, `apifaret`, `qualitycontrol`, `programa-produccion` (plus `calidad`/`fps`, routed via the web.config rewrite rules above rather than as IIS Applications). The certificate renews automatically via scheduled task `win-acme renew (acme-v02.api.letsencrypt.org)` (Let's Encrypt via win-acme). **If that renewal task fails, the cert expires and every app on that site breaks at once** with SSL/TLS trust errors that look like an app bug but aren't — if multiple unrelated production apps go down simultaneously, check this first: `schtasks /Query /TN "\win-acme renew (acme-v02.api.letsencrypt.org)" /V /FO LIST` and `powershell -Command "Get-ChildItem Cert:\LocalMachine\My | Select Subject,NotAfter"`.

## Architecture

### Client structure (`lib/`)

- `app/quality_control_app.dart` — root `MaterialApp`, launches on `WelcomePage`.
- `core/api/` — thin HTTP layer:
  - `api_client.dart` — `ApiClient` wraps `http` GET/POST against `ApiClient.baseUrl`, which is a compile-time `String.fromEnvironment('API_BASE_URL')`. The literal `defaultValue` in source has drifted between local/LAN URLs and the production URL across past commits — always check the current line rather than trusting history, and always build/run with an explicit `--dart-define=API_BASE_URL=...` rather than relying on the default.
  - `catalogos_api.dart` / `control_api.dart` — typed calls to specific endpoints (see below). `ControlApi.guardarRegistro` takes an optional attachment as **`Uint8List? archivoBytes` + `String? archivoNombre`** (not `dart:io File`) and sends it via `http.MultipartFile.fromBytes` — this works unmodified on both Android and web. Do not reintroduce `dart:io`/`File`/path-based file APIs in this file or in the two pages below; `dart:io` doesn't work on Flutter web.
- `core/utils/turno_calculator.dart` (2026-08-17) — `calcularTurno(DateTime)` returns `'A'`/`'B'`/`'C'` by time-of-day (A 07:00–14:29, B 14:30–23:29, C 23:30–06:59). Replaced a previously-hardcoded `'A'` turno across `control_form_page.dart`, `control_measurements_page.dart`, and the new `producto_terminado_form_page.dart` — before this, "turno" in every saved record was silently always `'A'` regardless of actual time, with no real logic anywhere in the app or backend.
- `core/local/` — SharedPreferences-backed persistence, the backbone of offline support:
  - `offline_catalog_store.dart` — caches the entire catalog (users, QR→machine/process/form contexts, visual parameters, wave types, materials, lab tests) as one JSON blob, seeded on first run from `assets/data/offline_catalog_seed.json` if nothing has been downloaded yet.
  - `cached_users_store.dart` — separate cache of the users list.
  - `pending_records_store.dart` — queues control records created while offline as `{localId, createdAt, endpoint, status, payload}`, to be flushed later.
- `core/network/network_mode_service.dart` — `NetworkModeService.shouldUseOfflineMode()` decides online/offline by checking `connectivity_plus` and then pinging `GET {baseUrl}/health` with a timeout; any failure means offline mode.
- `features/` — screens, one subfolder per flow:
  - `welcome/` — area/operator selection, entry point.
  - `home/home_page.dart` — hub: triggers catalog refresh (`ControlApi.descargarCatalogoOffline`), shows pending-record count, and flushes the pending-records queue (loops `PendingRecordsStore.getPendingRecords()` → `ControlApi.guardarRegistro()` → `removePendingRecord()`, reporting how many synced vs. remain). The arrow-cell positions come from a derived formula (`idx = aqlColIndex + letraRowIndex - 16`, 0-indexed), not a lookup table typed in by hand — deliberately, to avoid the transcription-error risk of hand-copying a 16×26 grid from an image; the formula was cross-validated against the app owner's own worked example, which itself had a typo the owner caught and corrected mid-session (see Claude Code memory for this project, `project_producto_terminado_nch44_status.md`, for the full story if revisiting this).
    - `presentation/producto_terminado_form_page.dart` — the whole flow in one page: NP→cliente/ítems (reuses `OrdenFabricacionApi`, same pattern as `control_form_page.dart`), proceso PT dropdown (Termoformado/Pegado) that lazily loads that proceso's `parametrosVisuales`/`origenesProblema` (reused as-is from the existing catalogs, proceso_id 4/5 — see backend section), multiple ID-pallet entries, nivel+AQL selectors with a live read-only NCh44 plan display, and a list of "hallazgos" (1 hallazgo = 1 unidad no conforme, correlativo automático, max-3-defectos, origen único, **foto realmente obligatoria** — blocking, unlike the generic control-form flow — "Otro" defecto → observación obligatoria, observación ≤120). "Máquina" is a **plain manual `TextField`** (`_maquinaController`) — an earlier version used a dropdown from `/api/catalogos/maquinas` filtered to Termoformado/Pegado with manual-text fallback (technically allowed by the original requirement's own escape clause, "manual, salvo que ya exista catálogo apropiado reutilizable"), but the app owner's explicit final call was strict literal "manual" — don't reintroduce the dropdown without asking again. Turno is `calcularTurno(DateTime.now())` (see `core/utils/` above), inspector is read-only (see `home_page.dart` above). "FINALIZAR INSPECCIÓN" asks for physical-sample-review confirmation, then computes `resultado` (`unidadesNC <= Ac → CONFORME`, `>= Re → NO CONFORME`, no editable override) and posts via `core/api/producto_terminado_api.dart` (multipart, one photo file per hallazgo, correlated by array index — same pattern as `calidad_faret_api.dart`'s multi-file upload but with a strict 1:1 hallazgo↔file count check server-side).

Client never talks to MySQL directly — everything goes through the REST API. When offline, records are written to `PendingRecordsStore` instead of POSTed, and reads fall back to `OfflineCatalogStore`.

### Backend structure (`backend/`)

- `server.js` — Express app entry point. CORS is locked to a hardcoded `allowedOrigins` allowlist (edit this array when adding a new client origin — as of 2026-07-20 it includes `https://workspace.faret.cl` and `https://qualitycontrol.faret.cl`, no path/trailing slash on either); serves `/uploads` statically for uploaded photos; exposes `GET /api/health` (checks the MySQL pool, also used by `NetworkModeService` to decide online/offline — a CORS rejection here makes the web app permanently report "offline mode" even with a working connection) plus the two route groups below. **Debugging tip:** a missing origin here is a silent failure mode — `curl`/Postman without an `Origin` header get a clean 200, so the API looks "up" while a real browser gets nothing. Test with `curl -H "Origin: https://the-domain" ...` or check the browser console, not just a plain request.
- `src/config/database.js` (git-ignored, not in repo) — `mysql2/promise` connection pool; `database.example.js` is the template.
- `src/routes/catalogos.routes.js` + `src/controllers/catalogos.controller.js` — `GET /api/catalogos/usuarios`, `/procesos`, `/maquinas`, `/parametros-visuales/:procesoId`, `/origenes-problema/:procesoId` (2026-08-17, new — reads table `origenes_problema`), and `/offline` (the combined payload consumed by `OfflineCatalogStore`, now also bundling `origenesProblema` per `qrContext`, filtered by `processId` same as `parametrosVisuales`).
- `src/routes/control.routes.js` + `src/controllers/control.controller.js` — `GET /api/control/contexto/:codigoQr` (resolves a scanned QR to machine/process/form + relevant visual params/wave types/materials/lab tests, and — 2026-08-17 — `origenesProblema` for that `processId`) and `POST /api/control/registros` (creates a control record; accepts an optional `multipart/form-data` photo via `multer`, stored under `backend/uploads/control/`; accepts an optional `origenId` since 2026-08-17, stored in `registros_control.origen_id`). Writes are transactional across `registros_control`, `registro_adjuntos`, `registro_fallas_visuales`, and `registro_ensayos` — roll back and delete the uploaded file on any failure.
- `src/routes/productoTerminado.routes.js` + `src/controllers/productoTerminado.controller.js` (2026-08-17, new) — `POST /api/producto-terminado/registros` (`multipart/form-data`, `payload` JSON field + `fotos` files array, up to 100, `multer` — strictly requires `hallazgos.length === files.length`, files correlated to hallazgos by array index), `GET /registros` (paginated, filterable by fecha/procesoPt/resultado), `GET /registros/:id` (full detail: cabecera + pallets + hallazgos + each hallazgo's defectos + origen — built for the not-yet-implemented Photino desktop consumer). Writes are transactional across `registros_producto_terminado`, `registro_pt_pallets`, `registro_pt_hallazgos`, `registro_pt_hallazgo_defectos` — reuses the existing `origenes_problema` and `parametros_control_visual` catalogs (proceso_id 4=Pegado/5=Termoformado) rather than separate PT-specific catalog tables; those catalogs already happened to contain exactly the Termoformado/Pegado defect lists this feature needed. Mounted in `server.js` under `/api/producto-terminado`.
- `src/routes/calidadFaret.routes.js` + `src/controllers/calidadFaret.controller.js` — `POST /api/calidad-faret/registros`, entirely independent of the `control` flow above: separate tables (`registros_calidad_faret`, `registro_calidad_faret_defectos`, `registro_calidad_faret_adjuntos`, already created in production), separate upload dir `backend/uploads/calidad_faret/` (up to 5 files, 10MB each, via `multer`). Payload arrives as a `payload` JSON string field (not raw JSON body) alongside `archivos` files, since it's `multipart/form-data`. Mounted in `server.js` under `/api/calidad-faret`. Also has `GET /registros`, `/resumen`, `/maquinas/resumen`, `/registros/:id/adjuntos` (read-only, for the future desktop reporting module). **`operador` fields (2026-07-21):** the payload/table carry three distinct operator fields — `operador`/`operador_otro` (required, the per-área/máquina dropdown from `calidad_faret_form_page.dart`) and `operador_registro` (nullable, the home-page-selected operator, added as a new column on `registros_calidad_faret` via `ALTER TABLE ... ADD COLUMN operador_registro VARCHAR(150) NULL` — do this migration on any environment before deploying this controller version). The `INSERT IGNORE INTO calidad_faret_operadores` (autocomplete-population side effect) reads from `operadorRegistro`, not `operador` — that table backs the home-page autocomplete, which is semantically "quien registra", not "operador de máquina".
- `src/routes/calidadFaretPallet.routes.js` + `src/controllers/calidadFaretPallet.controller.js` (2026-07-20) — pallet/papel checklist flow, entirely independent tables (`calidad_faret_pallet_preguntas`, `registros_calidad_faret_pallet`, `registro_calidad_faret_pallet_respuestas`). `POST /api/calidad-faret-pallet/registros` validates tipo material, dimensión/n° pallet required, checklist answers exactly match the active question set, observación required on NO_CUMPLE — plain JSON body (no `multer`, no attachments). Also `GET /preguntas`, `GET /registros` (paginated + filters), `GET /registros/:id`.
- `src/routes/calidadFaretOperadores.routes.js` + `src/controllers/calidadFaretOperadores.controller.js` (2026-07-20) — `GET /api/calidad-faret/operadores`, a single read-only endpoint backing the "Operador" autocomplete on `home_page.dart` (see Client structure above). Table `calidad_faret_operadores` (`nombre` UNIQUE, no per-area scoping) is grown organically: `crearRegistroCalidadFaretPallet` still does an `INSERT IGNORE` of the submitted `operador`; `crearRegistroCalidadFaret` does it from `operadorRegistro` instead as of 2026-07-21 (see the `calidadFaret.controller.js` entry above) — there is no separate "create operator" endpoint. Mounted in `server.js` *before* `/api/calidad-faret` (more-specific prefix registered first, though Express would fall through correctly either way since nothing under `/api/calidad-faret` itself matches `/operadores`).

Corrugated-specific fields (wave type, corrugated-specific merma/scrap fields) are only populated when `procesoId === 1`; other processes (Empalcado, Troquelado, Pegado, Termoformado, Paletizado, Producto Terminado — see the machine codes in `tools/generar_qr_maquinas.py`) send `null` for those columns.

### Known repo quirks

- `backend_publish_calidad_faret/` is a manual staging copy of 3 backend files (`server.js`, `src/routes/calidadFaret.routes.js`, `src/controllers/calidadFaret.controller.js`) meant to be copied to the production server (see the IIS/Node deployment notes above). It is **not auto-synced** with `backend/` — when editing any of those 3 files for a real fix (e.g. the CORS `allowedOrigins` array), update both copies, or the one you forgot silently reverts the fix on the next deploy. **Confirmed stale as of 2026-07-20, and again 2026-08-17** (the 2 new `productoTerminado.*` files added that day don't exist there at all) — do not use it as a deploy source until it's resynced; the 2026-08-17 deploy copied straight from `backend/` to the server instead, bypassing this folder entirely.
- **All `.md` files are gitignored as of 2026-07-20** (added `*.md` to `.gitignore`) because working-notes/deployment docs in this repo tend to contain internal IPs, share paths, and other infra details not meant for git history. `CLAUDE.md` itself was already tracked before this change, so it's unaffected (gitignore doesn't untrack already-tracked files) and continues to be edited/committed normally — but any *new* `.md` file (deployment runbooks, session continuation notes, etc.) will silently not show up in `git status`/`git add -A`. If you need one committed, `git add -f <file>.md` explicitly.
- `quality_control/` and `__MACOSX/` at the repo root are a leftover extracted zip copy of this same project (untracked, not part of the build) — ignore them when searching/editing. `flutter analyze` recurses into `quality_control/` too (it has its own unresolved `.dart_tool`) and produces ~1000+ unrelated errors from it — when checking analyzer output, filter to paths starting with `lib\`/`lib/` at the repo root, not `quality_control\`.
- `pubspec.yaml` pins `mobile_scanner: 5.2.3` and `image_picker: 1.2.3` (bumped from older 3.x/0.8.x pins specifically to fix web-target compile errors against the currently installed Flutter/Dart SDK — older pins failed `flutter build web` with errors inside the plugins' own web implementations, unrelated to app code). `environment.sdk` is `">=3.10.0 <4.0.0"` because `image_picker 1.2.3` requires `^3.10.0`. If bumping these further, re-verify `flutter build web --release` actually compiles, not just `flutter analyze`.
- `connectivity_plus` was bumped `3.0.6` → `^6.1.0` and `file_picker` `^5.2.11` → `^11.0.2` (2026-07-07) — both were capping a transitive `win32` dependency at `4.1.4`, which fails to compile against the currently installed Dart SDK (`Type 'UnmodifiableUint8ListView' not found`) and, separately, `connectivity_plus: 3.0.6` doesn't declare an AGP 8 `namespace` (see the Android build section above). The bumps changed call sites, already updated: `NetworkModeService.shouldUseOfflineMode()` in `network_mode_service.dart` now handles `Connectivity().checkConnectivity()` returning `List<ConnectivityResult>` (a single value pre-6.x), and the 3 file-attachment pickers (`calidad_faret_form_page.dart`, `control_form_page.dart`, `control_measurements_page.dart`) call `FilePicker.pickFiles(...)` directly — the `FilePicker.platform` static accessor was removed in file_picker 11.x.
